# 어쨌든, 바이브 코딩 실습

『어쨌든, 바이브 코딩』의 튜토리얼을 따라 실습하며, 만든 앱과 AI에게 전달한 개발 요청, 변경 과정을 함께 보관하는 저장소입니다. 완성된 코드뿐 아니라 어떤 요청으로 앱을 만들고 수정했는지도 다시 살펴볼 수 있도록 기록합니다.

## 저장소 구성

현재는 프로젝트 작업 지침, 실습 기록 스킬과 PR 템플릿이 준비되어 있습니다. `tutorials/`와 각 튜토리얼 폴더는 실습을 시작할 때 생성합니다.

아래는 튜토리얼을 시작한 뒤의 구성 예시입니다.

```text
anyway-vibe-coding/
├── README.md                         # 저장소 소개와 사용 방법
├── AGENTS.md                         # AI 작업 지침과 Git 규칙
├── .github/
│   └── PULL_REQUEST_TEMPLATE.md       # PR 본문 공통 양식
├── skills/
│   └── vibe-coding-tutorial-log/
│       ├── SKILL.md                  # 실습 폴더 생성 및 단계 기록 규칙
│       └── agents/openai.yaml        # 스킬의 에이전트 설정
└── tutorials/
    └── tutorial-01/
        ├── README.md                 # 실습 제목, 목표, 실행 방법
        ├── app/                      # 실습 앱의 현재 코드
        └── steps/                    # 개발 요청별 기록
            ├── 01-create-app.md
            ├── 02-add-feature.md
            └── 03-fix-error.md
```

튜토리얼 번호는 `tutorial-01`, `tutorial-02`처럼 최소 두 자리로 표기합니다. 각 튜토리얼은 독립된 폴더에서 관리합니다.

## 실습이 저장되는 방식

### 앱 코드(app/)

각 튜토리얼의 `app/`에서 하나의 앱을 계속 수정합니다. 개발 단계마다 앱 전체를 복사하지 않으며, 커밋한 시점의 코드는 Git 이력으로 확인할 수 있습니다.

### 개발 단계 기록(steps/)

앱 생성, 기능 추가, 수정, 오류 해결 요청은 `steps/`에 순서대로 저장합니다. 사용자 개발 요청 하나가 기록 한 개에 대응하며, 하나의 요청에 여러 기능이 있어도 같은 단계에 기록합니다.

각 기록에는 다음 내용이 들어갑니다.

- **상태**: 진행 중, 완료, 일부 완료 등 실제 작업 상태
- **사용자 프롬프트 원문**: 입력한 요청을 줄바꿈, 코드, 오류 메시지까지 그대로 보존
- **AI 응답**: 구현 설명과 처리 결과. 요약한 경우 `AI 응답 (요약)`으로 표시
- **생성·변경 내용**: 실제로 변경한 파일 경로와 주요 변경점

새로운 수정 요청은 다음 번호의 파일에 기록합니다. 과거 오류나 요청은 해결된 뒤에도 보존하고, 기존 기록을 정정하거나 보충할 때는 추가 내용을 구분해 남깁니다.

일반 질문, 코드 설명, 실습 관리 방식 논의, Git 작업 요청 자체는 앱 개발 단계로 기록하지 않습니다. 튜토리얼 폴더 생성만 요청한 경우에도 개발 단계 파일은 만들지 않습니다.

### 실행 방법과 결과(README.md, steps/)

튜토리얼별 `README.md`에는 사용자가 제공한 실습 제목과 목표를 적습니다. 제공되지 않은 내용은 `미제공`으로 표시하고, 실행 방법은 실제 앱 구성과 설정을 확인한 뒤 추가합니다.

실행 결과는 사용자가 명시적으로 기록을 요청할 때만 해당 단계에 추가합니다. 사용자 보고와 AI가 직접 확인한 결과를 구분하며, “잘 돼” 같은 동작 확인만으로는 자동 저장하지 않습니다.

## 실습 진행 예시

AI와 작업할 때 다음과 같이 요청할 수 있습니다.

1. **튜토리얼 시작**
   > 튜토리얼 1번 폴더 만들어줘. 제목은 할 일 앱, 목표는 할 일 추가와 삭제야.

   튜토리얼 폴더와 README를 생성합니다. 앱 구현은 별도의 개발 요청이 있을 때 시작합니다.

2. **앱 개발**
   > 튜토리얼 1번 앱에 할 일 추가 기능을 만들어줘.

   같은 `app/`에서 개발하고, 요청과 처리 내용을 `steps/`의 다음 단계에 기록합니다.

3. **실행 결과 기록**
   > 방금 단계에 실행 결과로 “할 일 추가 정상 동작”을 기록해줘.

   해당 단계에 사용자 보고임을 표시해 결과를 추가합니다.

4. **커밋과 푸시**
   > 깃 커밋 메시지 작성해서 push 해줘.

   해당 개발 요청의 코드와 기록을 함께 커밋하고 기능 브랜치를 푸시합니다.

5. **튜토리얼 완료**
   > 튜토리얼 실습 끝! main 브랜치에 merge 해줘.

   최종 앱과 기록을 검증하고 기능 브랜치 → develop PR을 생성합니다. AI가 PR 링크와 권장 병합 방식을 안내하면 사용자가 직접 병합 버튼을 누릅니다. 병합 완료를 알리면 AI가 원격 상태를 확인하고 develop → main PR, main → develop 동기화 PR을 순서대로 준비합니다. 각 PR의 최종 병합은 사용자가 직접 수행합니다.

튜토리얼 완료 요청과 별개로 PR 생성만 요청할 수도 있습니다.

> main 브랜치에 병합하기 위해 PR 올려줘.

AI는 소스·대상 브랜치와 변경 범위를 확인하고 필요한 커밋·푸시를 수행한 뒤 정해진 양식으로 PR을 생성하거나 기존 PR을 갱신합니다. PR 생성 요청 자체로 튜토리얼 완료를 선언하지 않습니다.

## Git 관리 방식

튜토리얼의 중간 개발 이력과 최종 완료 이력을 나누어 관리합니다.

| 브랜치 | 용도 |
| --- | --- |
| `main` | 완료한 튜토리얼과 반영을 요청받은 환경 설정 |
| `develop` | 완료 작업 통합 및 다음 기능 브랜치의 기준 |
| `feature/tutorial-NN` | 해당 튜토리얼의 모든 개발 단계와 중간 커밋 |
| `feature/<short-description>` | 작업 지침, 기록 스킬, 문서 등 환경 설정 작업 |
| `hotfix/<short-description>` | main에 반영된 내용의 긴급 수정 |

개발 요청만으로 커밋·푸시하거나 튜토리얼 완료를 선언하지 않습니다. 커밋·푸시 요청은 현재 기능 브랜치의 변경을 커밋하고 푸시하는 작업까지 진행합니다. PR 생성 요청 또는 튜토리얼 완료 및 병합 요청은 필요한 커밋·푸시와 PR 생성·갱신까지 진행합니다. **AI는 PR을 준비하고, 최종 병합 버튼은 사용자가 직접 누릅니다.**

다른 브랜치에 변경을 반영하기 전에는 반드시 PR을 올립니다. 환경 설정, hotfix와 main → develop 동기화에도 같은 규칙을 적용합니다. 로컬에서 먼저 병합한 뒤 대상 브랜치를 직접 푸시하는 방식으로 PR 절차를 우회하지 않습니다.

튜토리얼 완료 시에는 아래 순서로 진행하며, 각 PR의 사용자 병합을 확인한 뒤 다음 PR을 준비합니다.

| 순서 | PR 방향 | 권장 병합 방식 |
| --- | --- | --- |
| 1 | `feature/tutorial-NN` → `develop` | Create a merge commit: 중간 커밋 이력 보존 |
| 2 | `develop` → `main` | Squash and merge: 튜토리얼당 하나의 완료 커밋 |
| 3 | `main` → `develop` | Create a merge commit: main의 완료 커밋과 병합 관계 반영 |

다음 튜토리얼의 기능 브랜치는 최신 develop에서 생성합니다. main에만 반영된 환경 설정이 있으면 먼저 main → develop PR을 생성하고 사용자가 병합한 것을 확인한 뒤 develop을 갱신합니다. 같은 브랜치의 원격 변경을 로컬에 가져오는 작업에는 PR이 필요하지 않습니다.

커밋 메시지는 `<type>(<scope>): <summary>` 형식을 사용합니다.

```text
feat(tutorial-01): add todo creation
fix(tutorial-01): correct todo deletion
docs(repo): add repository readme
```

상세한 작업 경계, 커밋 메시지와 병합 절차는 [AGENTS.md](AGENTS.md)를 따릅니다.

## PR 작성 양식

PR 제목은 커밋 메시지와 같은 `<type>(<scope>): <summary>` 형식으로 전체 변경을 요약합니다. 본문은 모든 PR에서 **변경 내용**과 **실습 기록** 두 항목을 필수로 작성합니다.

```markdown
## 변경 내용
- 주요 변경 내용

## 실습 기록
- 튜토리얼 번호·이름
- 포함된 단계 또는 기록 경로
```

변경 내용은 실제로 만들거나 수정한 내용을 짧게 적고, 필요한 경우 이유를 함께 설명합니다. 실습과 무관한 지침·환경 설정 작업은 `해당 없음 (프로젝트 지침 수정)`처럼 이유를 적습니다. 새 기록이 없는 동기화 PR은 `새 실습 기록 없음 (브랜치 동기화)`으로 적습니다.

본문에는 검증이나 병합 방식 항목을 추가하지 않습니다. 필요한 검증 결과와 권장 병합 방식은 AI가 PR 링크와 함께 안내합니다. 공통 양식은 [PR 템플릿](.github/PULL_REQUEST_TEMPLATE.md)에 있습니다.
