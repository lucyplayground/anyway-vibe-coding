> 작성일: 2026-11-10
> 대상: `tutorials/tutorial-03/` (브랜치 `feature/tutorial-03`)
> 목적: 어제 실습에서 `gemini-3.8-flash` 호출이 실패하고 모델을 바꾸자 동작한 이유를 정리하고, 모델 교체 외에 다른 해결 방법이 있었는지, 이번 실습에서 무엇을 배웠는지 기록한다.

## 1. 한 줄 요약

`gemini-3.8-flash`가 실패한 이유는 **우리 코드나 API 키 문제가 아니라 Google 쪽 해당 모델 서버가 일시적으로 혼잡했기 때문**일 가능성이 가장 높다(HTTP 503 `service_unavailable`). 모델 교체는 이 상황에서 바로 쓸 수 있는 해결책 중 하나였지만 **유일한 방법은 아니었다**. 공식 문서가 먼저 권하는 방법은 "잠시 기다렸다가 점점 간격을 늘려 다시 시도(exponential backoff)"이고, 실서비스라면 재시도 + 대체 모델(fallback)을 함께 쓰는 것이 정석이다.

## 3. 원인 분석

### 3.1 에러 코드가 말해 주는 것

HTTP 상태 코드는 "누구 잘못인지"를 구분하는 첫 단서다. 공식 API 오류 문서 기준으로 정리하면:

| 코드 | 의미 | 원인 위치 | 공식 권장 조치 |
|---|---|---|---|
| 400 | 요청 형식·파라미터 오류 | **내 코드** | 요청 수정. 재시도 금지 |
| 401/403 | 키 오류·권한 없음 | **내 키/프로젝트** | 키·프로젝트 상태 확인 |
| 404 `model_not_found` | 모델 이름이 없음 | **내 설정** | "모델 이름을 확인하거나 다른 모델로 fallback" |
| 429 | 분당/일일 한도 초과 | **내 사용량** | 백오프 후 재시도, 할당량 확인 |
| **503 `service_unavailable`** | **"서비스가 일시적으로 과부하 상태이거나 중단됨"** | **Google 서버** | **"기다렸다가 exponential backoff로 재시도"** |
| 504 `deadline_exceeded` | 마감 시간 내에 끝나지 않음 | 요청 시간 설정/서버 | "클라이언트 마감 설정을 없애거나 늘려 서버 기본값 사용" |

우리가 받은 것은 **503**이었다. 이 사실만으로 다음을 알 수 있다.

- 요청이 Google 서버까지 **정상적으로 도달**했고, 서버가 형식에 맞는 오류를 돌려줬다 → 네트워크·요청 형식 문제는 아님.
- 키가 틀렸거나 모델 이름이 틀렸다면 401/403/404가 나왔을 것 → 키·모델명 문제도 아님.
- 할당량 초과라면 429가 나왔을 것 → 사용량 문제도 아님.
- Google 포럼의 공식 안내 글(2026-02-20, Google 직원 작성)도 **"503 오류는 할당량과 무관하며 서비스가 일시적으로 과부하라는 뜻"** 이고 **"하루 중 특정 시간대에 더 흔하다"** 고 설명한다.

즉 **"코드는 맞게 짰는데, 그 시간에 그 모델의 서버가 붐볐다"** 가 가장 그럴듯한 설명이다.

### 3.2 처음의 "시간 초과"는 무엇이었나

503 이전에 먼저 겪은 증상은 응답 지연이었다. 여기에는 두 가지 요인이 겹쳤던 것으로 보인다.

1. **추론(thinking) 기본값**: 공식 문서에 따르면 Gemini 3.x 모델은 기본으로 추론을 켜고, `gemini-3.8-flash`의 기본 추론 수준은 `medium`이다. 문제 해결 가이드도 "Gemini 3.x는 추론이 기본 활성화라 지연·토큰 사용이 늘 수 있으니, 지연이 중요하면 추론 수준을 낮추라"고 안내한다. 색상 다섯 개 뽑기는 깊은 추론이 필요 없는 작업이라 `low`로 낮춘 것은 올바른 조치였다. (`minimal`은 3.8 Flash에서 지원하지 않아 오류가 난다.)
2. **서버 혼잡**: 서버가 붐비면 요청이 늦게 처리되거나 아예 503으로 거절된다. 추론 수준을 낮춘 뒤에도 503이 나온 것은 남은 원인이 우리 쪽 설정이 아니라 서버 쪽 용량이었다는 뜻이다.

> step 04 기록에 남긴 "시간 제한을 늘려도 Gemini의 서비스 오류 자체를 해결할 수는 없다"는 판단이 정확했다.

### 3.3 왜 모델을 바꾸니 됐나

서버 용량은 **모델별로** 따로 운영된다. 503은 "Gemini 전체"가 아니라 "그 모델을 돌리는 서버"가 붐빈다는 신호인 경우가 많다.

| | `gemini-3.8-flash` (기존) | `gemini-3.5-flash-lite` (교체 후) |
|---|---|---|
| 성격 | 최신 Flash 계열 주력 모델 | 공식 문서상 **Stable** 모델 |
| 공식 설명 | 기본 추론 `medium`, 복잡한 작업에 토큰을 더 쓰도록 설계 | "저지연·저비용, 대량 처리에 최적화", 단순 데이터 추출 등에 적합 |
| 수요 | 신규 주력 모델이라 요청이 몰리기 쉬움 | 상대적으로 덜 붐빔 |
| 우리 작업 적합도 | 과한 편 | 색상 5개 JSON 생성에 충분 |
| 구조화 출력(JSON) | 지원 | 지원 |

정리하면 **가장 최신·인기 모델이 그 시점에 붐볐고, 가볍고 안정적인 모델은 여유가 있었다.** 게다가 컬러 팔레트 생성은 Flash-Lite로도 충분한 단순 작업이라, 결과적으로 이 앱에는 교체한 모델이 더 잘 맞는 선택이기도 하다.

### 3.4 확실하지 않은 부분 (정직하게 남겨 두기)

- **3.8 Flash로 다시 시도해 보지 않았다.** 몇 분~몇 시간 뒤라면 3.8 Flash도 정상 동작했을 수 있다. 모델 교체가 "필수"였는지는 확인되지 않았다.
- **API 키도 비슷한 시기에 바뀌었다.** 모델 교체 직후 새 키로 모델 목록을 조회했다. 포럼에는 "특정 계정/프로젝트에서만 503이 계속 나고 다른 키로 바꾸니 됐다"는 사례(2026-02)도 있어서, 키(프로젝트) 교체가 영향을 줬을 가능성을 완전히 배제할 수는 없다. 다만 사용자가 체감한 변화는 "모델 바꾸니까 됨"이었다.
- **모델을 바꿔도 503이 날 수 있다.** 2026-09 포럼 글에서는 3.6 / 3.7 / 3.8 Flash가 동시에 503을 내고 "모델을 바꿔도 503"이라는 보고가 있었다. 모델 교체는 확률을 높이는 방법이지 보장은 아니다.
- 해당 날짜의 Google 공식 장애 기록은 찾지 못했다.

## 4. 모델을 바꾸는 방법밖에 없었나?

**아니다.** 상황별로 쓸 수 있는 방법을 정리하면:

| 방법 | 효과 | 이번 실습에서 | 비고 |
|---|---|---|---|
| ① **잠시 후 재시도 (exponential backoff + jitter)** | 일시적 혼잡이면 그대로 해결 | 수동으로만 시도, 코드에는 없음 | **공식 1순위 권장.** 1초→2초→4초→8초처럼 간격을 늘리고, 무작위 지연(jitter)을 더하고, 최대 횟수를 정한다. 429·5xx만 재시도하고 400·403은 재시도하지 않는다 |
| ② **대체 모델(fallback) 자동 전환** | 한 모델이 붐벼도 다른 모델로 응답 | 수동으로 `.env`를 바꿔 해결 | 예: `3.8-flash` 실패 → `3.5-flash-lite`로 재요청. 공식 오류 문서도 모델 문제 시 fallback을 언급한다 |
| ③ **작업에 맞는 가벼운 모델을 기본값으로** | 애초에 덜 붐비고 빠른 모델 사용 | **결과적으로 이것을 선택** | 단순 작업엔 Flash-Lite가 비용·지연 모두 유리 |
| ④ 추론 수준 낮추기 | 지연·비용 감소 | `low`로 적용함 | 503 자체는 못 막음 |
| ⑤ 시간 제한 늘리기 | 504 감소 | 60초/75초로 늘림 | 공식 문서는 504에 대해 클라이언트 마감을 없애거나 늘리라고 안내. 503에는 효과 없음 |
| ⑥ 붐비지 않는 시간대 이용 | 503 빈도 감소 | — | 공식 안내: 503은 특정 시간대에 더 흔함 |
| ⑦ 유료 등급·Priority 추론 옵션 | 처리 우선순위 향상 | — | 실습 규모에는 과함. Priority 등급에서도 503이 났다는 보고가 있어 만능은 아님 |
| ⑧ Batch API | 비실시간 대량 처리에 적합 | — | 버튼 누르면 바로 결과가 나와야 하는 이 앱에는 맞지 않음 |
| ⑨ AI Studio에서 프로젝트 상태 확인 | 계정 단위 문제 진단 | — | 계속 503이면 Restricted / Payment needed 등의 표시가 있는지 확인 |

**결론:** 실습 상황에서는 "모델 교체"가 가장 빠르고 현실적인 해결이었다. 하지만 근본적인 대응은 **①재시도 + ②fallback** 을 코드에 넣어 사용자가 직접 `.env`를 고치지 않아도 되게 만드는 것이다.

## 5. 현재 코드에서 발견한 개선 포인트 (아직 반영하지 않음)

1. **기본 모델값 불일치**: 실제 `.env`는 `gemini-3.5-flash-lite`인데, `app/gemini.mjs`의 기본값(`model = 'gemini-3.8-flash'`), `app/.env.example`, `README.md`는 여전히 `gemini-3.8-flash`다. 새로 클론한 사람은 다시 같은 문제를 겪을 수 있다.
2. **재시도 로직 없음**: 503/429/504가 오면 바로 사용자에게 오류를 보여 준다. 1~2회 자동 재시도(백오프)를 넣으면 체감 실패가 크게 줄어든다.
3. **fallback 모델 없음**: `GEMINI_FALLBACK_MODEL` 같은 설정을 두고 503일 때 한 번 더 요청하는 방식을 생각해 볼 수 있다.
4. **step 04 상태**: "일부 완료"로 남아 있다. 모델 교체로 해결된 결과와 이 문서를 반영해 갱신하면 좋다.
5. **커밋 대기**: Gemini 통합 이후 변경은 아직 미커밋 상태다(`AGENTS.md` 변경과는 분리해서 커밋).

## 6. 이번 실습에서 배운 것

### 6.1 에러 코드를 먼저 읽자
"안 된다"는 같아 보여도 400·403·404·429·503은 원인이 전혀 다르다. 특히 **4xx는 내 쪽, 5xx는 서버 쪽**이라는 큰 구분만 알아도 엉뚱한 곳(내 코드, 키)을 고치느라 시간을 쓰지 않는다. 이번에는 503이었기 때문에 코드를 아무리 고쳐도 해결되지 않았던 것이다.

### 6.2 "최신 = 최선"이 아니다
가장 최신 모델은 성능이 좋지만 수요가 몰리고, 추론을 기본으로 많이 해서 느릴 수 있다. 색상 다섯 개처럼 단순한 작업에는 **가볍고 안정적인 모델이 더 빠르고 싸고 덜 실패한다.** 모델은 작업 난이도에 맞춰 고르는 것이다.

### 6.3 설정을 코드 밖으로 빼 둔 덕을 봤다
모델 이름을 `GEMINI_MODEL` 환경 변수로 받게 만들어 둔 덕분에 **코드 수정 없이 `.env` 한 줄만 바꿔서** 문제를 우회할 수 있었다. API 키도 `.env`에 두고 `.gitignore`로 제외해 대화나 Git에 노출되지 않았다. "바뀔 수 있는 값은 설정으로"라는 원칙의 실전 사례다.

### 6.4 외부 API는 실패하는 것이 정상이다
외부 서비스는 언제든 느려지거나 거절할 수 있다. 그래서 다음을 미리 준비해야 한다.
- 시간 제한(서버 60초 < 브라우저 75초처럼 순서 있게)
- 사용자에게 보여 줄 친절한 오류 메시지 (이번 앱은 503·504·429를 구분해서 안내함)
- 재시도와 대체 경로 (이번 앱에 아직 없는 부분)

### 6.5 모의 테스트와 실제 호출은 다르다
모의 응답 테스트 7개는 처음부터 통과했지만 실제 Gemini 호출은 실패했다. 모의 테스트는 "내 코드가 응답을 올바르게 처리하는가"를 검증하고, 실제 호출은 "외부 서비스가 지금 응답해 주는가"를 검증한다. **둘 다 필요하다.**

### 6.6 변수는 한 번에 하나씩 바꾸자
이번에는 모델 교체와 API 키 교체가 비슷한 시기에 일어나서, 정확히 무엇이 해결의 열쇠였는지 100% 단정할 수 없게 됐다. 문제를 진단할 때는 **한 번에 하나만 바꾸고 결과를 확인**하는 습관이 원인을 확실하게 남겨 준다.

### 6.7 바이브 코딩에서도 공식 문서와 기록이 힘이 된다
AI에게 "공식 문서를 참고해 줘"라고 요청하고, 매 단계를 `steps/`에 기록해 둔 덕분에 하루가 지난 오늘도 무슨 일이 있었는지 재구성할 수 있었다. AI가 만든 코드라도 **왜 그렇게 동작하는지 근거를 남겨 두는 것**이 다음 문제를 빨리 푸는 열쇠다.

## 7. 다음에 같은 문제가 생기면 (체크리스트)

1. 응답의 **HTTP 상태 코드**와 오류 메시지 확인
2. 4xx → 키·모델 이름·요청 형식·할당량 확인 / 5xx → 서버 쪽 문제로 보고 다음 단계로
3. 잠시(1~2분) 기다렸다가 재시도
4. 계속되면 **더 가벼운 모델**로 `GEMINI_MODEL` 교체 후 서버 재시작
5. 그래도 안 되면 AI Studio에서 프로젝트 상태 확인, 다른 시간대에 시도
6. 해결되면 무엇을 바꿨는지 `steps/`에 기록
