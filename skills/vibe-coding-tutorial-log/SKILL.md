# 바이브 코딩 튜토리얼 기록

튜토리얼마다 하나의 앱 프로젝트를 이어서 개발하고 개발 요청과 처리 내용을 보존한다. 기록은 한국어 Markdown으로 작성하되 사용자 프롬프트와 코드·오류 메시지는 원래 표현을 유지한다. 사용자가 제공하지 않은 책의 내용, 실습 제목, 목표, 구현 요구사항을 추측하지 않는다.

## 저장 위치와 튜토리얼 선택

- 실습 루트는 `anyway-vibe-coding/`이며 튜토리얼은 그 아래 `tutorials/`에 둔다. 스킬 원본이 `<실습 루트>/skills/vibe-coding-tutorial-log/`에 있으면 해당 루트를 사용한다. 스킬을 다른 곳에 설치한 경우 현재 작업 폴더와 사용자 지정 경로에서 실습 루트를 확인한다. 후보가 여러 개여서 구분할 수 없으면 확인을 요청한다.
- 번호는 최소 두 자리로 표현한다. 예: 1 → `tutorial-01`, 12 → `tutorial-12`, 100 → `tutorial-100`.
- 대상은 사용자가 명시한 번호, 현재 대화에서 진행 중인 튜토리얼, 현재 작업 중인 `tutorial-NN/app/` 경로로 판단한다. 대상이 불분명하면 확인하고 임의로 가장 최근 폴더를 선택하지 않는다.

## 시작 또는 폴더 생성

“튜토리얼 N번 시작하자” 또는 “튜토리얼 N번 폴더 만들어줘”라는 요청을 받으면 다음 구조를 생성한다.

```text
tutorials/tutorial-01/
├── README.md
├── steps/
└── app/
```

1. 기존 파일과 폴더를 먼저 확인한다. 없는 폴더와 파일만 생성하며 기존 내용은 이어서 사용한다. 기존 README를 템플릿으로 덮어쓰지 않는다.
2. README에 사용자가 제공한 실습 제목과 목표를 작성한다. 아직 제공되지 않았다면 `미제공`으로 표시한다. 이후 사용자가 제공하면 해당 부분만 보완한다.
3. 실행 방법은 `app/`의 실제 프로젝트 구성과 설정을 확인한 뒤 추가한다. 프레임워크, 설치·실행 명령, 포트 등을 추측하지 않는다. 실행을 직접 확인하지 않았다면 확인했다고 표현하지 않는다.
4. 시작·폴더 생성 요청만으로 앱을 구현하거나 개발 단계 파일을 만들지 않는다. 같은 요청에 앱 개발 지시가 포함되면 그 요청은 아래 규칙에 따라 기록하고 수행한다.
5. `screenshots/` 폴더는 생성하지 않는다.

새 README의 최소 형식:

```markdown
# 튜토리얼 01

## 실습 제목
미제공

## 목표
미제공
```

제목과 목표가 제공되면 `미제공` 대신 사용자 내용을 넣는다. 실행 방법 섹션은 프로젝트 구성이 확인되었을 때만 추가한다. 루트 README 작성 등 요청하지 않은 실습 관리 작업을 추가하지 않는다.

## 자동 단계 기록의 범위

해당 튜토리얼 앱의 생성, 기능 추가, 수정, 오류 해결 요청은 별도 기록 요청 없이 저장한다. 한 번의 사용자 개발 요청을 한 단계로 취급한다. 하나의 요청에 여러 기능이 들어 있어도 프롬프트를 임의로 여러 단계로 나누지 않는다.

다음 대화는 새 개발 단계로 기록하지 않는다.

- 개념 설명, 일반 질문, 코드 설명만 요청하는 대화
- 폴더 구성, 기록 방식, 스킬 제작 등 실습 관리 방법을 논의하는 대화
- “잘 돼”, “안 돼”, “실행했어” 등 동작 여부만 알려주는 대화
- 실행 결과를 기록해 달라는 요청만 있는 대화: 아래 실행 결과 규칙으로 처리

“오류가 나니 고쳐줘”처럼 수정·문제 해결 의도가 있는 요청은 개발 단계에 포함한다. 오류 메시지가 개발 요청에 들어 있으면 프롬프트 원문과 오류 해결 내용으로 보존한다. 이를 실행 결과를 자동으로 추가할 근거로 삼지 않는다.

## 단계 파일 생성과 앱 개발

1. `steps/`의 기존 Markdown 파일을 확인한다. 파일명의 시작 숫자 중 최댓값에 1을 더해 다음 순번을 정한다. 빈 폴더는 `01`부터 시작하며 삭제된 번호의 빈자리를 재사용하지 않는다.
2. `01-create-app.md`, `02-add-search.md`, `03-fix-build-error.md`처럼 최소 두 자리 순번과 짧은 소문자 영문 설명을 붙인다. 같은 이름이 이미 있으면 덮어쓰지 말고 순번을 다시 확인한다.
3. 작업 시작 시 사용자 메시지 원문을 저장하고 상태를 `진행 중`으로 남긴다. 맞춤법, 띄어쓰기, 줄바꿈, 코드 블록, 오류 메시지를 고치거나 요약하지 않는다. 관리 설명과 개발 지시가 섞인 메시지도 개발 요청이 있으면 전체 메시지 원문을 보존한다.
4. 코드는 해당 튜토리얼의 `app/`에 저장한다. 기존 앱을 먼저 확인하고 같은 프로젝트를 수정한다. 단계마다 앱 전체를 복사하거나 별도의 앱을 만들지 않는다.
5. 작업 뒤 AI 응답과 생성·변경 내용을 채우고 상태를 `완료`, `일부 완료`, `중단` 등 실제 상황에 맞게 갱신한다. 실패나 미해결 오류도 남긴다. 기록만 작성하고 개발 작업을 수행한 것처럼 표현하지 않는다.
6. AI 응답은 사용자에게 전달하는 구현 설명·처리 결과를 기록한다. 내부 추론은 기록하지 않는다. 최종 응답을 요약해서 저장해도 되지만 반드시 `AI 응답 (요약)`이라고 표시한다. 원문이라고 표시할 때는 실제 응답 원문을 그대로 보존한다.
7. 생성·변경 내용에는 실제 변경한 파일 경로와 핵심 변경점을 적는다. 변경이 없으면 그 사실과 이유를 적는다. 실행 결과는 기본 단계 양식에 넣지 않는다.
8. 앱 구성이 확인되거나 실행 명령이 바뀌면 튜토리얼 README의 실행 방법을 실제 설정에 맞춰 보완한다. 기존 제목과 목표 등 다른 내용은 보존한다.

단계 파일의 기본 형식:

````markdown
# 01. 앱 생성

- 상태: 진행 중

## 사용자 프롬프트 원문
```text
사용자가 실제 입력한 전체 메시지
```

## AI 응답 (요약)
작업 후 실제 응답의 요약을 작성한다.

## 생성·변경 내용
- `app/내/파일경로`: 실제 생성 또는 변경 내용
````

원문에 백틱 코드 울타리가 있으면 그보다 긴 울타리를 사용해 원문이 손상되지 않도록 한다. 양식의 예시 문구를 실제 작업 결과로 남기지 않는다.

## 실행 결과와 기록 보존

- 실행 결과는 사용자가 명시적으로 기록해 달라고 요청할 때만 추가한다. 사용자의 동작 확인이나 AI가 수행한 빌드·테스트 결과를 자동으로 단계 파일에 추가하지 않는다. 검증을 수행하고 사용자에게 보고하는 것은 가능하지만 로그에 실행 결과로 저장하려면 명시적 기록 요청이 필요하다.
- 요청이 있으면 해당 단계에 `실행 결과 (사용자 요청으로 추가)` 섹션을 추가한다. 사용자 보고인지 AI가 직접 확인한 결과인지 출처를 구분하고 실제로 제공되거나 관찰된 사실만 적는다. 대상 단계가 불분명하면 확인한다. 실행 결과 기록 요청 자체로 새 개발 단계를 만들지 않는다.
- 기존 프롬프트, AI 응답, 오류 기록은 보존한다. 새로운 수정 요청은 새 순번의 단계 파일에 저장한다. 해결되었다는 이유로 과거 오류를 삭제하지 않는다.
- 과거 기록을 정정·보충할 때는 원래 기록을 남기고 `정정` 또는 `보충` 섹션에 대상, 이유, 추가 내용을 적어 변경 사실이 드러나게 한다. 실행 결과를 후속으로 추가할 때도 기존 결과를 덮어쓰지 않는다.
- 같은 요청의 진행 중 기록을 마무리할 때는 해당 파일의 상태와 미작성 응답·변경 내용을 완성한다. 이후 별도의 개발 요청을 기존 단계에 합치지 않는다.
- Git 커밋과 GitHub 업로드는 사용자가 요청했을 때만 수행한다. 튜토리얼 시작이나 개발 요청만으로 커밋·푸시하지 않는다.

## 사용 예시

- `튜토리얼 1번 폴더 만들어줘. 제목은 할 일 앱, 목표는 할 일 추가와 삭제야.` → 구조와 README를 만들고 앱 개발 요청을 기다린다.
- `튜토리얼 1번 앱에 할 일 추가 기능을 만들어줘.` → 같은 `app/`를 개발하고 다음 단계 파일에 자동 기록한다.
- `삭제 버튼을 눌러도 항목이 남아 있어. 고쳐줘.` → 진행 중인 튜토리얼 앱을 수정하고 새 단계로 기록한다.
- `이제 잘 돼.` → 실행 결과를 자동 저장하지 않는다.
- `방금 수정한 단계에 실행 결과로 “삭제 버튼 정상 동작”을 기록해줘.` → 해당 단계에 사용자 보고임을 표시해 실행 결과를 추가한다.
